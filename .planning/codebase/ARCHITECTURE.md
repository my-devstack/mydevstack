## Pattern Overview

**Overall:** Hexagonal Architecture (Ports & Adapters) for Go backend + Component-Based SPA for Vue frontend.

**Key Characteristics:**
- Dependency direction points inward: ports define contracts in `internal/ports/`, adapters in `internal/adapters/` implement them, `internal/proxy/` provides the concrete `ProxyService` that wires ports to adapters
- `internal/application/` acts as composition root (manual DI, no code generation)
- Frontend mirrors the service-per-directory pattern: 20+ AWS services each have their own API client module, composable, component folder, and view
- Frontend uses feature folder layout: composables are in `composables/`, components per service in `components/<service>/`, views in `views/services/`
- Both Go and Vue have comprehensive test coverage (unit + integration + storybook + e2e)

## Layers

**Go Backend (`pkg/proxy/`):**

**Entry Point:**
- Purpose: Parse environment/config, create DI container, start HTTP server + schedulers
- Location: `pkg/proxy/cmd/server/main.go`
- Contains: `main()`, `loadConfig()`, `defaultConfig()`, `getEnv()`
- Depends on: `internal/application`, `internal/config`
- Used by: Go runtime

**Application/Composition Root:**
- Purpose: DI wiring, route registration, server lifecycle management, scheduler lifecycle
- Location: `pkg/proxy/internal/application/`
- Contains: `Container struct`, `NewContainer()`, `RunServer()`, `RunScheduler()`, `setupRoutes()`
- Depends on: `internal/adapters/*`, `internal/cache`, `internal/config`, `internal/proxy`, `internal/version`
- Used by: `cmd/server/main.go`

**Ports (Interfaces):**
- Purpose: Define contracts for input (service) and output (AWS client, cache, GitHub) ports
- Location: `pkg/proxy/internal/ports/`
- Contains: `ProxyService`, `S3Port`, `LambdaPort`, etc., `S3ClientPort`, `CachePort`, `GitHubClientPort`, `VersionServicePort`
- Depends on: AWS SDK v2 types (output only)
- Used by: `internal/proxy`, `internal/adapters/*`, `internal/version`

**Ports (Handler Interfaces):**
- Purpose: Define service interfaces consumed by HTTP handlers (subset of full ports)
- Location: `pkg/proxy/internal/adapters/http/interfaces.go`
- Contains: `S3Service`, `LambdaService`, etc. — per-service interfaces
- Depends on: AWS SDK v2 types
- Used by: `internal/adapters/http/*.go`

**Domain/Service Layer:**
- Purpose: Concrete implementation of `ProxyService` port — manages AWS adapter lifecycle, region switching
- Location: `pkg/proxy/internal/proxy/`
- Contains: `ProxyService struct`, accessors for all 20+ services, `SetServices()`, `SetRegion()`
- Depends on: `internal/ports`, `internal/adapters/aws`, `internal/config`

**Version Service:**
- Purpose: Periodic GitHub release version check with cache/retry
- Location: `pkg/proxy/internal/version/`
- Contains: `VersionService`, `StartScheduler()`, `checkAndUpdateVersion()`, `GetLatestVersion()`
- Depends on: `internal/ports` (CachePort, GitHubClientPort)

**Cache:**
- Purpose: Simple in-memory TTL cache
- Location: `pkg/proxy/internal/cache/`
- Contains: `Cache struct` with `Get`, `Set`, `Delete`, `GetOrSet`
- Depends on: None (stdlib only)

**Config:**
- Purpose: Load configuration from YAML + env vars with defaults
- Location: `pkg/proxy/internal/config/`
- Contains: `Config struct`, `LoadConfig()`, `SetDefaults()`
- Depends on: `github.com/beabys/ayotl`

**Driving Adapters (HTTP Handlers):**
- Purpose: Accept HTTP requests, parse JSON, call service ports, return JSON responses
- Location: `pkg/proxy/internal/adapters/http/`
- Contains: `ProxyHandler`, `ServiceRouter` (switch on service name), per-service handler files
- Depends on: `internal/adapters/http/interfaces.go` (service interfaces), `gin-gonic/gin`

**Driven Adapters (AWS SDK):**
- Purpose: Wrap AWS SDK v2 clients, translate to internal port interfaces
- Location: `pkg/proxy/internal/adapters/aws/`
- Contains: One file per AWS service (S3, Lambda, DynamoDB, SQS, SNS, etc.)

## Data Flow

### Primary Request Path

1. **Browser** → makes HTTP request to Vite dev server (`:3000`) or production nginx
2. **Vite proxy** (`vite.config.ts`) → forwards path-based requests to Go backend (`:8081`) based on service prefix (`/s3`, `/lambda`, `/dynamodb`, etc.)
3. **Gin router** (`application/app.go:setupRoutes()`) → matches `/:service/*path`, applies CORS middleware
4. **ProxyHandler.ServiceRouter** (`adapters/http/handlers.go:82`) → switches on `c.Param("service")` to dispatch to per-service handler
5. **Service handler** (e.g., `handleS3`) → inspects `X-Amz-Target` header, dispatches to specific action method
6. **Action method** (e.g., `listBuckets`) → calls `h.Svc.S3().ListBuckets(ctx)` on the `ProxyService` facade
7. **ProxyService** (`proxy/service.go`) → delegates to the AWS adapter (e.g., `aws.S3Adapter`)
8. **AWS adapter** (`adapters/aws/s3.go`) → calls AWS SDK v2 client method against configured endpoint
9. **Response** flows back: AWS SDK → adapter → ProxyService → handler → Gin → Vite proxy → browser

### Region Switching

1. Client sends `POST /proxy/region` with `{"region": "eu-west-1"}`
2. `ProxyHandler.SetRegion` → calls `h.Svc.SetRegion(region)`
3. `ProxyService.SetRegion` → locks mutex, updates region, calls `SetServices()` to recreate all AWS adapters with new region
4. All subsequent requests use the new region's AWS configuration

### Version Check Flow

1. `Container.RunScheduler` starts a `time.Ticker` at configurable interval (default 24h)
2. `VersionService.StartScheduler` runs; first check immediate, then on tick
3. `checkAndUpdateVersion` → fetches latest GitHub release via `GitHubClientPort` with retry (max 2, 5min delay)
4. Result cached in-memory with 25h TTL; served to `/health` endpoint
5. Frontend sidebar polls `/health` to display version update notification

### Frontend Data Flow

1. Vue component (e.g., `S3.vue` view) → imports composable `useS3()`
2. Composable → calls API functions from `@/api/services/s3.ts`
3. API module → uses `api.get/post/etc` from `@/api/client.ts`
4. Client → axios instance with mock SigV4 signing → sends request to Vite proxy → Go backend

**State Management:**
- Pinia stores for cross-component state: `settings` (credentials, region, theme), `ui` (sidebar, loading, modals)
- Composable-local `ref()` for per-service state (lists, selections, loading flags)
- No server-side state management — all state is fetched on component mount or user action

## Key Abstractions

**ProxyService (Facade):**
- Purpose: Central interface providing access to all 20+ AWS service ports; manages region lifecycle
- Example: `pkg/proxy/internal/ports/service.go:33` (interface), `pkg/proxy/internal/proxy/service.go` (implementation)
- Pattern: Facade + Interface Segregation — each service has its own narrow port interface, combined into one `ProxyService` composite interface

**Port per AWS Service:**
- Purpose: Each AWS service (S3, Lambda, DynamoDB, etc.) has two-level ports:
  1. Low-level `{Service}ClientPort` in `internal/ports/aws_client.go` — mirrors AWS SDK exactly
  2. High-level `{Service}Port` in `internal/ports/service.go` — used by HTTP handlers and ProxyService
- Pattern: Interface segregation with adapter layer hiding SDK complexity

**Per-Service HTTP Handler Files:**
- Purpose: Each AWS service gets its own handler file (`adapters/http/{s3,lambda,...}.go`) with X-Amz-Target dispatch
- Pattern: Action dispatcher at the top, individual handler methods below; consistent parseBody → call → c.JSON pattern

**Composable per Service (Vue):**
- Purpose: Each AWS service has a `use{Service}()` composable encapsulating all state, API calls, and toast notifications
- Pattern: Returns `{state refs, action functions}` — components import and destructure what they need

## Entry Points

**Go Server:**
- Location: `pkg/proxy/cmd/server/main.go`
- Triggers: `make run-proxy` → `go run ./pkg/proxy/cmd/server`
- Responsibilities: Config loading, DI container creation, HTTP server startup, scheduler startup, graceful shutdown

**Vue App:**
- Location: `pkg/ui/src/main.ts`
- Triggers: `make run-ui` → `pnpm run dev` (Vite dev server)
- Responsibilities: App creation, Pinia + Router installation, mount

## Architectural Constraints

- **Threading:** Go backend uses `errgroup` for concurrent server + scheduler lifecycle; `sync.RWMutex` protects shared state (region, cache); `sync.RWMutex` for health check cache; `sync.RWMutex` for version state
- **Global state:** `pkg/proxy/internal/proxy/service.go` — region mutex-protected field; `pkg/ui/src/api/client.ts` — singleton `apiClient` variable; `pkg/proxy/internal/version/version.go` — mutable `retryDelay` package var overridden in tests
- **Circular imports:** Not detected — dependency direction is enforced by hexagonal architecture (ports in center, adapters outside)
- **Single-writer region:** `SetRegion()` acquires write lock and recreates ALL adapters — all concurrent requests are blocked during region switch

## Anti-Patterns

### Duplicate Interface Definitions

**What happens:** `ports/service.go` defines service interfaces (e.g., `S3Port`), and `adapters/http/interfaces.go` defines nearly identical interfaces (e.g., `S3Service`) — these are two separate interface hierarchies with subtle differences (e.g., `S3Port` has 20 methods, `S3Service` has 9)
**Why it's wrong:** Code duplication requires keeping two interface sets in sync; HTTP handler interfaces are subsets that may drift from the actual port interfaces
**Do this instead:** Define the full port interfaces once in `internal/ports/` and have the HTTP handlers depend on the full `ports.ProxyService` interface (the handler already does this via `ports.ProxyService` for its `Svc` field)

### Massive Port Files

**What happens:** `internal/ports/aws_client.go` is 399 lines with 20+ interfaces; `internal/ports/service.go` is 401 lines with a single `ProxyService` interface + 20+ port interfaces
**Why it's wrong:** Large interface files reduce discoverability; adding a new service requires modifying the same monolithic files
**Do this instead:** Split into one file per service port (e.g., `ports/s3.go`, `ports/lambda.go`) following the same pattern as `internal/adapters/aws/` and `internal/adapters/http/`

## Error Handling

**Strategy:** Go backend uses `sendError()` helper that JSON-marshals errors with `"error"` key; errors are logged server-side. Vue frontend has `APIError` class and interceptor that translates HTTP errors to user-facing toasts.

**Patterns:**
- Go: `if err != nil { sendError(c, http.StatusXXX, "message", err); return }` in handlers
- Go: `fmt.Errorf("...: %w", err)` for error wrapping in adapters
- Vue: `try { ... } catch (error) { toast.error('...') }` in composables
- Vue: Axios interceptor catches network/CORS errors; 5xx errors shown as toasts; 4xx errors logged but not toasted (expected)

## Cross-Cutting Concerns

**Logging:** Go: `log.Printf` standard library (no structured logging library); Vue: `console.error` for non-user-facing errors
**Validation:** Go: `parseBody()` helper with JSON key transformation (lowercase → TitleCase); Vue: Inline validation in forms
**Authentication:** Mock SigV4 signing via `X-Mock-Signature` header; no real AWS auth in local dev mode
